# 对外测试任务 API（REST）开发规格

> **文档性质**：内部开发计划与接口设计说明，供实现前评审与分工。产品用户文档应发布在 `site/docs`；本文件不替代 OpenAPI 终稿。

## 1. 背景与目标

当前测试/攻击任务主要依赖 Web 界面手动创建与操作。本需求在**不替代**现有内部 `Authorization: Bearer <JWT>` 能力的前提下，为集成方（CI、调度系统、合作方）提供**仅基于 API 密钥**的对外 REST 接口，实现任务创建、状态查询、结果/回调等自动化编排。

**非目标（首版可明确排除或后置）**：

- 不承诺与所有历史内部路由 1:1 行为一致；对外 API 以稳定、可版本化的资源模型为准。
- 不将「管理后台全部能力」一次性对外暴露；按「最小可用 + 可扩展」开放。

## 2. 你方已列需求（必须满足）

| 项 | 说明 |
|----|------|
| 任务创建 | 与现有业务约束一致（组织、配额、目标配置、检测配置等）的创建能力，请求体可基于现有 `POST /api/v1/attack-tasks` 的 Zod 结构做**对外子集/别名**或显式版本化 DTO。 |
| 完成回调 | 任务进入终态（成功/失败/取消等）时，向集成方 URL 发送 HTTP 通知；需定义重试、签名与幂等。 |
| 任务列表 | 分页、筛选（状态、时间范围、名称等）、排序；默认仅返回当前 API 密钥可见范围。 |
| 任务状态 | 轻量轮询接口（含进度字段若已有）；与详情接口职责划分清晰。 |
| 任务详情 | 含结果摘要、错误信息、关联资源 ID 等；敏感字段脱敏策略见下文。 |
| Agent 列表 | 对外「可选探测目标/Agent」列表（与现有 `target-agents` 等业务对齐）；需定义租户隔离与权限。 |
| RESTful | 资源名词复数、标准 HTTP 动词、合理状态码；集合与单资源路径区分。 |
| API 密钥 | 支持生成、轮换、吊销；支持**过期时间**或**永不过期**（含风险提示与 UI/管理约束）。 |

## 3. 建议补充的「必需 / 强烈建议」开发点

以下为对外 API 常见缺口，建议在首版或紧随其后的版本中落地，否则易出现安全事故或集成困难。

### 3.1 身份认证与授权模型

- **鉴权方式**：建议统一使用 `Authorization: Bearer <api_key>` 或专用请求头（如 `X-Api-Key`），并在文档中**只选一种**对外公布，避免客户端混乱。
- **与 JWT 会话隔离**：对外密钥不应等同于用户登录态；建议在服务端将 API Key 解析为「服务主体」：`organizationId`、可选 `createdByUserId`、**权限范围（scopes）**、**可见资源边界**。
- **Scopes（权限粒度）**：例如 `tasks:read`、`tasks:write`、`agents:read`、`webhooks:receive`（若双向）、`callbacks:configure`；默认最小权限原则。
- **密钥存储**：仅存密钥的**哈希**（如 bcrypt/argon2），明文仅在创建/轮换时展示一次；数据库字段与日志严禁落明文。

### 3.2 API 版本与路由前缀

- 建议使用独立前缀，例如：`/api/v1/external/...` 或 `/public/v1/...`，与现有内部 `/api/v1/*` 并列，便于网关策略（限流、IP 允名单、审计）分离。
- **破坏性变更**必须 bump 版本（`/v2`），或在同版本下仅 additive 变更并文档化。

### 3.3 请求幂等与重放防护

- **创建任务**：支持可选请求头 `Idempotency-Key`（UUID），在 TTL（如 24h）内重复提交返回同一任务，避免网络重试导致重复任务。
- **回调投递**：对同一 `taskId + terminalStatus` 的notify 应**幂等**（集成方可能多次收到，应以业务 ID 去重）。

### 3.4 回调（Webhook）设计要点

| 主题 | 建议 |
|------|------|
| 注册方式 | 创建任务时在 body 中带 `callbackUrl`（单次），和/或组织级默认 Webhook 配置（管理 API）。 |
| 签名 | 使用 HMAC-SHA256（或同类），密钥为单独 **Webhook Secret** 或与 API Key 派生；请求头携带时间戳与签名，防篡改与防重放。 |
| 重试 | 指数退避 + 最大次数；4xx 中除 408/429 外是否继续重试需明确策略。 |
| 超时 | 较短连接超时，避免阻塞任务收尾线程；失败记入投递队列或审计。 |
| 载荷 | 包含 `event`、`taskId`、`status`、`occurredAt`、`links`（详情 URL）等；大对象放详情 API 拉取。 |

### 3.5 速率限制与配额

- **全局限流**：按 API Key / 组织维度 QPS、每日请求数；响应头返回 `X-RateLimit-*`。
- **业务配额**：与现有「攻击任务月度配额」等打通；超限返回 **429** 或 **403**（与现网一致），错误码 machine-readable。

### 3.6 分页、排序、过滤（列表类接口）

- 统一查询参数：`page`/`cursor`、`limit`（上限封顶）、`sort`、`order`、`status`、`createdAfter`/`createdBefore`、`q`（名称搜索）等。
- 响应包含：`items`、`total` 或 `nextCursor`，避免客户端盲翻页。

### 3.7 错误模型与国际化

- 保持与现有 API 风格一致（如 `{ success: false, error: { code, message, details } }`），**code** 稳定供程序分支。
- `message` 可为默认语言；若需 i18n，可用 `Accept-Language` 或固定英文 + 文档说明。

### 3.8 安全与合规

- **仅 HTTPS**（生产）；文档声明不支持明文。
- **敏感数据**：日志按仓库规范脱敏（密钥、Authorization、回调 body 中的配置等）。
- **审计**：密钥创建/吊销、权限变更、高危操作留痕（可与现有 enterprise 审计对齐）。
- **CORS**：对外若为服务端调用，通常不必放宽浏览器 CORS；若存在浏览器直连则需单独评估。

### 3.9 可观测性与运维

- **Metrics**：按路由、组织、keyId（哈希维度）统计 QPS、延迟、4xx/5xx。
- **Tracing**：`X-Request-Id` 贯穿网关→应用→回调投递。
- **告警**：回调失败率、限流触发率、密钥暴力探测（401 暴增）。

### 3.10 契约与文档

- **OpenAPI 3.1**（或 3.0）单文件发布；示例请求/响应与错误码表同步维护。
- **Postman Collection** 或同类可作为附录生成物。

### 3.11 测试策略

- 契约测试（schemathesis / openapi-validator）。
- 集成测试：创建任务 → 模拟终态 → 断言回调签名与重试。
- 安全测试：无效密钥、过期密钥、吊销密钥、跨租户 ID 越权。

## 4. REST 资源草案（示例，实现时以 OpenAPI 为准）

以下为建议的资源划分，路径前缀以 `/api/v1/external` 为例。

| 方法 | 路径 | 说明 |
|------|------|------|
| `POST` | `/tasks` | 创建任务（body 对齐业务 DTO 子集） |
| `GET` | `/tasks` | 任务列表（分页/筛选） |
| `GET` | `/tasks/:taskId` | 任务详情 |
| `GET` | `/tasks/:taskId/status` | 轻量状态（可选；若与详情重复可合并） |
| `DELETE` | `/tasks/:taskId` | 取消任务（若业务支持） |
| `GET` | `/agents` | 可选 Agent/目标列表（命名以产品为准） |
| `POST` | `/api-keys` | 创建 API 密钥（仅管理角色或独立「密钥管理」权限） |
| `GET` | `/api-keys` | 列举密钥元数据（不可回显现钥） |
| `DELETE` | `/api-keys/:keyId` | 吊销 |
| `POST` | `/api-keys/:keyId/rotate` | 轮换（可选独立端点） |

说明：

- **回调 URL** 可在 `POST /tasks` 的 body 中携带，或通过组织级 Webhook 配置（若实现则增加 `GET/PATCH /webhooks/default` 等）。
- **获取 agent 列表**若与现网 `target-agents` 同源，对外 DTO 应剥离内部字段，仅暴露集成所需 ID、名称、类型等。

## 5. API 密钥与有效期（数据模型要点）

| 字段（概念） | 说明 |
|--------------|------|
| `id` | 密钥记录 UUID |
| `prefix` | 可存储明文前缀用于列表展示（如 `pk_live_xxxx`） |
| `secretHash` | 哈希存储 |
| `organizationId` | 租户 |
| `expiresAt` | 可空；`null` 表示永不过期 |
| `scopes` | 字符串数组或位图 |
| `status` | `active` / `revoked` |
| `lastUsedAt` | 可选，用于审计与闲置吊销策略 |

**永不过期**：产品侧需提示泄露风险；可选策略为「仅企业版允许」或「必须绑定 IP 允名单」。

## 6. 与现有代码库的对齐点（实现参考）

- 任务创建校验与落库可参考 `backend/src/server/routes/api/v1/attack-tasks.ts` 中 `createTaskSchema` 与 `POST /` 处理逻辑。
- 中间件：现有 JWT 鉴权在 `backend/src/server/routes/api/v1/index.ts`；对外密钥需**新增**独立中间件，避免与登录态混用。
- 数据库：使用 Drizzle 新增 `api_keys`（命名待定）表及迁移；与 `organizations` / 配额服务关联。

## 7. 里程碑建议

1. **M1**：数据模型 + 鉴权中间件 + `POST/GET /tasks` 只读联调。
2. **M2**：列表分页、详情、取消（若需要）、agent 列表。
3. **M3**：回调签名、重试、幂等键、限流。
4. **M4**：OpenAPI、集成测试、运维告警与审计。

---

## 8. 开放问题（评审前需拍板）

- 对外 API 是否允许 **跨组织** 超级管理员密钥，还是严格一组织一池密钥？
- 回调是否必须 **公网可达**，是否支持 **mTLS** 或固定 egress IP 列表（双向信任）？
- 任务结果中的漏洞详情、原始请求是否默认包含，还是分级 scopes？
