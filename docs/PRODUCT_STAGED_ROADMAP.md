# DodoGuard 分阶段产品逻辑：从扫描器到控制平面

**文档目的**：把能力建设按「商业闭环」拆成四个递进阶段，每阶段只优先少数可交付项，避免在早期过度投入复杂协同。  
**原则**：阶段一不做大而全协作；阶段二对齐企业采购与签单；阶段三对齐续费与运营粘性；阶段四对齐叙事与融资尽调。

---

## 总览：一条主链路

```mermaid
flowchart LR
  S[扫描器 / 探测] --> V[验证平台]
  V --> G[发布门禁]
  G --> M[治理平台]
  M --> C[控制平面]
```

| 阶段 | 从 → 到 | 商业重心 |
|------|---------|----------|
| 一 | 扫描器 → **验证平台** | 结果可信、可复现，先立住「测得准」 |
| 二 | 验证平台 → **发布门禁** | 工程嵌入 + 阈值 + 例外，利于 **签企业单** |
| 三 | 发布门禁 → **治理平台** | 人、时间、工单、SLA，利于 **续费** |
| 四 | 治理平台 → **控制平面** | 策略、合规、组织视图，利于 **融资叙事** |

---

## 阶段一：扫描器 → 验证平台

**目标**：把「有没有问题」说清楚——同一输入可重复得到同一结论，评级与基线可被引用、被审计。  
**刻意不做**：跨团队复杂协同流、大规模工作流编排（此步不急）。

### 优先补齐（按优先级）

| 能力 | 说明 |
|------|------|
| **风险评级标准** | 严重级别定义、与 CVSS / 内部等级的映射规则、版本化（改标准要留痕）。 |
| **安全基线模板** | 可复用的检查模板（如 Agent 类型、数据分级、环境）；与评级标准绑定。 |
| **通过 / 失败判定** | 明确判定来源：规则 / 模型辅助 / 人工；输出结构化 verdict，禁止仅「看一眼算过」。 |
| **回归测试集** | 固定用例集 + 版本；用于版本升级与策略变更后的对比。 |
| **结果可复现** | 配置哈希、数据快照、模型/策略版本、运行环境记录；支持「同配置重跑」对齐结论。 |

### 阶段一完成判据（示例）

- 客户能用同一基线模板对同一目标重复运行，**结论一致或在文档化容差内**。  
- 任意一次「失败」可指向：**哪条规则/哪条用例/哪个版本**。  

### 与现有能力的关系

- 对齐评测 / 红队 / 配置审计的**输出契约**（结构化结果 + 元数据），而非再堆新扫描形态。

---

## 阶段二：验证平台 → 发布门禁

**目标**：把验证嵌进 **交付流水线**，让「上线前必须满足」可自动化执行、可阻断、可例外审批。  
**商业重心**：**最利于签企业单**（安全与工程双负责人都听得懂）。

### 优先补齐（按优先级）

| 能力 | 说明 |
|------|------|
| **API** | 触发扫描/验证、拉取结果、查询门禁状态；稳定鉴权（Token/密钥）、幂等与限流。 |
| **Webhook** | 任务完成、超阈、门禁失败等事件推送，便于接内部平台。 |
| **CI/CD 集成** | GitHub Actions / GitLab CI 等官方或文档化模板；PR/MR 评论回写结果链接。 |
| **风险阈值** | 按严重级别、数量、类型配置「阻断 / 警告」；与组织/仓库/环境维度可选绑定。 |
| **审批与例外机制** | 临时放行、带期限例外、关联责任人/工单 ID（可先轻量：备注 + 过期时间 + 审计记录）。 |

### 阶段二完成判据（示例）

- 一次 MR 可在 CI 中跑完门禁，**失败可阻断合并**；例外路径有记录、可过期。  
- 安全团队不必登录 UI 也能通过 API/Webhook 接到结论。  

### 与阶段一依赖

- 无稳定 **通过/失败判定** 与 **可复现结果**，门禁无法服众；阶段二是阶段一的「出口产品化」。

---

## 阶段三：发布门禁 → 治理平台

**目标**：从「单次门禁」变成 **持续运营**：谁负责、是否超时、历史是否变好。  
**商业重心**：**最利于续费**（粘性在流程与责任，不在单次工具使用）。

### 优先补齐（按优先级）

| 能力 | 说明 |
|------|------|
| **任务调度** | 定时扫描、周期基线校验、事件触发（如配置变更后重跑）。 |
| **资产视图** | 目标 Agent / 应用 / 环境维度的聚合仪表盘；与发现、门禁历史关联。 |
| **历史趋势** | 风险数量、级别分布、门禁通过率随时间变化；支持按资产/团队切片。 |
| **修复工单** | 与 ITSM 对接（内置网关 + 适配器）；Finding ↔ 外部单号。 |
| **责任人** | 资产/任务/发现的归属；通知与升级路径（可先简单指派）。 |
| **SLA** | 超期未处理提醒、报表；与责任人、工单状态联动。 |

### 阶段三完成判据（示例）

- 管理层能回答：**这个月比上个月是更好还是更差**、**谁 backlog 最重**。  
- 客户续费理由可落在「治理数据」而非「又扫了一次」。  

### 与阶段二依赖

- Webhook/API 已存在时，调度与告警成本更低；门禁阈值是 SLA 与趋势统计的输入之一。

---

## 阶段四：治理平台 → 控制平面

**目标**：多资产、多平台、多合规框架下的 **统一策略与可视边界**——偏战略与融资叙事。  
**商业重心**：**最利于融资**（品类高度、护城河、可扩展性）。

### 优先补齐（按优先级）

| 能力 | 说明 |
|------|------|
| **多资产关系图** | 应用、模型、数据存储、外部 API、Agent 工具链等关系可视化（可先做只读图 + 手工边）。 |
| **跨平台策略** | Policy-as-Code：同一策略在 CI、API、运行时检查（若做）中的一致表述与版本。 |
| **数据基线** | 数据分级、驻留、处理者清单与扫描发现的交叉视图（敏感数据暴露类问题归位）。 |
| **合规映射** | 发现项映射 OWASP LLM、MITRE ATLAS、内部合规条款；导出对审计友好。 |
| **权限模型** | 组织/团队/资产级 RBAC；审计员、开发、安全、管理员分离。 |
| **组织级报表** | 高管摘要、对比行业模板、年度/季度趋势简报（可部分自动化）。 |

### 阶段四完成判据（示例）

- 对外可用一张图讲清：**策略如何覆盖资产与流水线**；尽调可要到 **合规映射与权限说明**。  

### 与前几阶段依赖

- **合规映射** 依赖阶段一的标准化发现与评级。  
- **组织级报表** 依赖阶段三的趋势与资产聚合。  

---

## 实施纪律（避免跑偏）

1. **阶段一**：不急着做复杂协同（大工作流、多角色会签、复杂 BPM）；先把 **标准、基线、判定、回归、复现** 做扎实。  
2. **阶段二**：优先 **API / Webhook / CI / 阈值 / 例外**——直接服务企业采购与工程落地。  
3. **阶段三**：优先 **调度、资产、趋势、工单、人、SLA**——直接服务续费与客户成功。  
4. **阶段四**：在数据与权限具备后再加重 **控制平面** 叙事，避免空壳大屏。
