How to use this prototype

Follow the numbers once. Buttons that say “mock” or show a toast are not calling a backend. The only cross-page memory is sessionStorage for a scenario draft (optional), read by Run Center when you open it from Scenario Studio step 4.

  1. Test Data — Browse the dataset table. Use Details to open the drawer (import JSONL, manual row, scoring guide). Use Scenario / Run links to jump elsewhere with query params. You do not have to create data first; mock rows already exist.
  2. Scenario Studio — Tab Catalog lists fake scenarios. Click Edit or New scenario, then switch to Create / edit. Use Next through steps: Define → Matrix (datasets + counts) → Evaluate (rules / rubric) → Schedule. Step 1 requires a name before continuing.
  3. Evaluation rules (optional for the walkthrough) — Explains deterministic checks. Real attachment happens in Scenario Studio step 3.
  4. Run Center — Mock run list and filters. If you arrived with ?dataset=… or ?scenario=…, banners explain the link. New Run only shows a toast.

Design principles

Aligned with the Reliability Lab module.

  • Reliability-first: capability, robustness, stability, and efficiency over raw defect counts.
  • Scenario + Test Data as first-class, versionable assets.
  • Gates driven by quality metrics, not vulnerability tallies.

Glossary & data flow

How this static preview lines up with backend concepts.

  • Run: one evaluation execution in Run Center (you can prepend mock rows).
  • Scan task: mock job for scheduled or on-demand scans (policy / surface checks), separate from Runs. See Run Center → Scan tasks.
  • Task: durable orchestration unit in the product; schema in repo TASK_TABLE_SCHEMA.md. Run Center → Recent tasks is display-only mock.
  • Suggested flow: Test Data (question / expected answer / item type) → Scenario matrix binds a dataset → Run (and real Tasks in production). item_type labels stratification; pass/fail uses the same vars + rules + rubric path—see How items are scored.
