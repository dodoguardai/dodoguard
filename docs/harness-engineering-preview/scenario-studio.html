Scenario Studio

Scenario catalog and step wizard: define → data matrix → evaluation → execution plan.

Two tabs: Catalog = pick or start a scenario (click Edit or New scenario — you are moved to Create / edit automatically). Create / edit = the four-step wizard. Nothing is saved to a server; Save draft / Publish only show toasts. Full walkthrough → 说明：必须先填场景名称才能点 Next 进入第 2 步；从 Test Data 的 Scenario 链过来会带上数据集提示。

Edit syncs the Define step from that catalog row (mock; not persisted). Next requires a scenario name on step 1. Deep link: ?tab=editor&step=2|3|4 opens the wizard on that step; ?dataset=… still sets matrix datasets.

    Test matrix & failure injection

    Each row picks a dataset from Test Data (same IDs: cs-intent-gold-v3, etc.). Dataset rows are test cases: question (input), expected_answer (expected output / pass signal), optional failure_signals (must-not phrases, forbidden tools, bad-example hints), and item type (Factual, Reasoning, Tool-use, Safety, Robustness). Runtime intent: send each row's question to the bound agent, compare output against expected_answer via rules and/or rubric, then aggregate pass-rate. Step 3 Evaluate configures that scoring path (Promptfoo-style vars + assertions, mock). Use Item type below to stress the mix; add or remove rows; counts are editable. Matrix Item type drives mix / reporting for the row; Mixed means do not filter the dataset to a single type. The same scoring pipeline applies to every type—see Test Data · How items are scored.

    Evaluation

    Judge mode and attached assets determine how each matrix row is scored after the agent responds (mock only). Practical flow: question -> agent output -> rule/rubric match with expected_answer (and failure_signals) -> per-item result -> aggregated pass-rate / score.

    How this run is scored
    1. Execute each matrix row against the bound agent using each dataset item’s question as input; context for graders includes expected_answer, failure_signals, and item_type from Test Data. Deterministic rules do not branch on item_type in this preview (mock)—you author rules once; labels are for you and for rubric context.
    2. Rule checks run from the attached rule sets against captured output / tool trace (weighted sub-score).
    3. The LLM rubric model grades the response using your instructions below (weighted sub-score).
    4. Hybrid blend: rule sub-score and LLM sub-score are combined using the weights below, then compared to the pass threshold (per-item and roll-up in Run Center).
    1. Execute each matrix row against the bound agent using each dataset item’s question as input; expected_answer / failure_signals / item_type can inform how you author rules in Evaluation rules (mock). Rules do not auto-switch by item_type here (mock).
    2. Only rule sets run — no LLM rubric call. Each enabled rule is evaluated against output / tool trace.
    3. Aggregated rule pass / score is compared to the pass threshold. Tri-metric “Accuracy / Robustness / Efficiency” weights do not apply in this mode (mock).
    1. Execute each matrix row against the bound agent using each dataset item’s question as input; grader context includes row item_type when enabled below. No rule pass/fail by item_type in this mode (mock).
    2. Rule sets are skipped — no deterministic rule pass/fail in this mode.
    3. The LLM rubric alone produces a score (typically 0–1) from your grading instructions and the assembled context (see preview below).
    4. That rubric score is compared directly to the pass threshold. Multi-metric weights below do not apply (mock).
